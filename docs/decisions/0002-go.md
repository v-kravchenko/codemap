# 0002. Go, not Rust/Kotlin/the prototype's language

- Status: accepted
- Date: 2026-10-24

## Context

The tool started as an interpreted-language prototype (the earlier prototype mentioned in
0001/0004). Profiling the prototype on a real app (~35k classes, ~305k graph nodes, ~574k edges,
~155MB of class files) found the bottleneck was the interpreter and row-by-row SQLite, not the
analysis itself: a small-symbol query took 0.4-0.6s (mostly interpreter and database startup), a
wide query (impact of a base class used by hundreds of screens) took 7s, and a full rebuild took
about 9.4s. There was no realistic way to push an interpreted, row-at-a-time implementation much
below that ceiling.

A rewrite was decided on, and the language had to be picked before the rewrite started.

## Decision

Rewrite in Go. Build and ship single static binaries for Linux x64, macOS arm64, and Windows, with
no cgo, so a binary built on one machine cross-compiles for the others with
`CGO_ENABLED=0 GOOS=... go build`.

## Consequences

- A spike confirmed the approach before committing: parsing and hashing ~35k classes, building
  nodes and edges, and writing them out took about 4.6s total (with a pure-Go SQLite driver) or
  3.9s (with a cgo-based one); loading the built map and walking a wide query took 0.02s. The
  actual port came in faster still once it moved off SQLite entirely (0003) — full build around 3s,
  queries in tens of milliseconds.
- No cgo means the pure-Go SQLite driver was used wherever SQLite was still involved (export, and
  during the port, comparison against the prototype); it measured about 15% slower than a
  cgo-based driver, accepted as the cost of simple cross-compilation.
- Everything in the walk (graph traversal, bytecode parsing, resource/manifest/XML parsing, the
  JSON writer) had to be written from scratch; no existing Go library did any of it for this
  domain.

## Alternatives considered

- **Rust.** Not set up on the development machine and slower to write against a deadline; no
  concrete performance case was made that Rust would do meaningfully better than Go once the
  interpreter and row-by-row database were gone, so the extra setup and ramp-up cost wasn't
  justified.
- **Kotlin/JVM as a Gradle build-logic task.** Familiar to the team already working on the Android
  project, but a JVM process pays 0.2-0.5s of startup on every single-query invocation — a cost
  that a native binary skips entirely, and that was precisely the kind of per-query overhead the
  rewrite was meant to remove.
- **Keep the original language, optimize it.** Tried first, as described above: the ceiling was
  around 2-3s once the heaviest wins (parallel parsing, a stable query path) were applied, with
  further optimization fighting the interpreter itself. A faster interpreter-level runtime
  (PyPy-class) brought its own problems (slower native SQLite binding, or a JIT compiler that drops
  the "standard library only, no extra install" property) without removing the row-by-row database
  bottleneck.
